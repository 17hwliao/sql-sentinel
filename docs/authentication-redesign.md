# 两个控制台的 QQ 邮箱认证方案

设计日期：2026-10-23。实施状态：**两个控制台已替换 Clerk，完成 OIDC、加密 Redis 会话、CSRF、独立成员授权及部署初始化。真实 Casdoor + 隔离 SMTP 的浏览器注册／登录、SSO、权限及停用回归已通过；真实 QQ SMTP 投递尚未配置／验证。** 实际操作以 [Casdoor 手册](casdoor-runbook.md) 为准，以下保留设计依据与验收要求。

## 选择与适用范围

建议使用自托管 Casdoor 作为共享身份中心，通过 QQ 邮箱 SMTP 发送登录／注册验证码。两个产品保持独立的网页、BFF 和业务权限，不合并为同一个控制台。认证服务是基础设施，不承担网关账务、SQL 审批或业务租户授权。

选择依据是当前无法完成托管平台开发者注册，以及已有 Linux Docker Compose 部署目标。自托管后，允许哪些邮箱域名由自己配置，不必先获得另一个托管平台账号；真实 QQ 收信和服务器网络仍须验证。邮箱验证码登录与 QQ OAuth 扫码登录是两种能力；本方案只要求前者，无需申请 QQ 互联应用。

| 方案 | 当前判断 |
| --- | --- |
| 自托管 Casdoor + QQ SMTP | 本次建议：已有邮件验证码、OIDC/SSO 能力；需要自己部署、备份及更新身份服务 |
| 托管 Authing | 可选，官方有邮箱认证和邮件配置；开发者注册、套餐权益和 QQ 投递须先验证，暂不承诺无条件可用 |
| 托管 Supabase Auth | 支持邮件 OTP 和自定义 SMTP，但默认发信限制不能直接用于公开注册；仍有托管账号及网络前提 |
| 在两个 BFF 各写验证码和用户表 | 不采用；会形成两套身份、重复维护验证码、会话与撤销逻辑 |

QQ SMTP 适合先验证个人项目的少量邮件。发信频率、反滥用和送达能力由邮箱服务决定，不承诺批量发信或任意流量。以后可替换 SMTP 发信商，保留身份用户和两个产品的授权关系。

## 登录过程

1. 用户打开 AgentMesh 或 SQL Sentinel，点击邮箱登录。
2. 当前产品 BFF 建立短期、一次性的 OIDC 事务，保存 state、nonce、PKCE verifier 和允许的回跳路径，然后跳转到身份中心。
3. Casdoor 的业务应用显示中文邮箱验证码登录／注册页面，通过 QQ SMTP 发信；不在两个业务页面分别实现验证码校验。
4. 用户正确验证邮箱后，身份中心返回 authorization code 到该产品已登记的 callback。
5. BFF 使用标准 OIDC 客户端库交换 code，验证发行者、受众、签名、nonce、有效期及 PKCE；检查邮箱验证和用户可用状态。实际 claim 和状态接口按固定版本核实，不把缺失的 email_verified 当作 true。
6. BFF 使用稳定的外部身份 `(issuer, sub)` 映射本地用户，读取本产品的成员授权，再建立服务端会话。
7. 网关 BFF 使用服务端专用应用 Key 调用 Go 网关；SQL BFF 按本地成员权限换取现有 scoped token。浏览器既不持有模型平台 Key，也不持有后台管理凭据。

首次通过邮箱验证只证明身份，不自动授予管理员、模型余额或 SQL 项目访问权。当前演示用户由管理员分别绑定已有租户／项目；未来的自助开通应另有受限业务流程。

## 共享账号与独立权限

- 同一身份中心组织／用户池，建立两个 OIDC 应用：mesh-console、sentinel-console，各用自己的 client 和精确 callback 白名单。
- Casdoor 共享登录会话实现 SSO。用户从一个产品跳到另一个时，目标产品仍走自己的 OIDC 流程和成员检查；身份中心会话有效时通常不必再次输入验证码。不能用直接共享业务 Cookie 代替这一流程。
- 两个 BFF 的会话 Cookie 各自限定当前 host；生产采用 Secure、HttpOnly、SameSite=Lax，不设置父域共享 Cookie。令牌保存在服务端，不放 localStorage。
- 本地会话放共享 Redis 的独立前缀，支持删除、轮换、空闲／绝对过期和账号停用。最初建议空闲 30 分钟、绝对 8 小时，最终值可配置。
- 业务成员授权继续每次读取。身份停用／撤销的传播范围和时限必须用固定 Casdoor 版本实测，必要时通过服务端状态检查补齐；不能只验长期 JWT 就声称立即撤销。
- 界面区分“退出当前产品”与“退出所有产品”。前者撤销当前 BFF 会话；后者还结束身份中心会话并撤销两产品本地会话，未实现跨产品撤销前不展示后者为可用能力。
- 注册、邮箱变更、身份绑定与业务权限分开。不得按可变邮箱地址自动合并已有成员或授予别人的租户权限。

## 验证码和请求边界

目标策略为验证码短时有效、使用一次失效、限制尝试次数；初始拟设有效期 5 分钟、发送间隔至少 60 秒。先核实所选版本实际可配置项和重发失效语义，缺口在共享认证入口补齐，不虚构已有保证。

发送入口同时限制邮箱与来源 IP，并设置全局发信上限；异常流量触发身份中心内置图片验证码。限流状态必须跨实例共享，不能只存单进程。发送和校验失败要保留用户输入、提示等待或重试，不自动重复发信；验证码、授权码和会话令牌不写日志。

使用 Cookie 后，BFF 的业务写入需补齐 CSRF token／严格 Origin 校验。OIDC callback 单次消费，固定回跳白名单，拒绝开放重定向。缺失身份服务配置时继续拒绝真实业务操作，预览模式只使用模拟数据。

## 本地和服务器部署

- 本地继续保留两个独立控制台地址，另用身份中心本地地址；callback 必须与实际 origin 完全匹配。本地 loopback 可使用 HTTP，生产全部使用 HTTPS。
- 生产示意为 `mesh.<域名>`、`sql.<域名>`、`auth.<域名>`，原模型 API 入口另行保留。Caddy 反代到各自服务；认证数据库和 Redis 不开放公网端口。
- Casdoor 使用独立数据库/schema 和最小权限数据库账号，不复用业务数据库的 root 凭据。身份数据和必要配置纳入备份；SMTP 凭据通过私有配置挂载，不加入镜像和源码。
- 固定核实过的 Casdoor 镜像版本／摘要；替换示例管理员和示例凭据，只给业务组织配置公开注册；真实上线前还需为管理员配置受控访问入口。
- QQ SMTP 初始配置为 `smtp.qq.com`、465、隐式 TLS；用户名及发件人使用完整 QQ 邮箱，密码字段使用专门生成的授权码。后端或服务器负责连接 SMTP，用户电脑无需持续开机。

## 实施与验收顺序

1. 固定版本并启动隔离身份服务，先用受控 SMTP 和测试身份核实验证码、OIDC、Cookie、CSRF、权限与撤销行为。
2. 取得 QQ SMTP 私有授权码，只向用户明确指定的测试邮箱发送最少必要验证码，核实服务端接受、实际送达和登录；SMTP 接受不等于收件箱已收到。
3. 用同一真实账号登录两个产品，验证独立授权、切换、退出、停用；未授权注册用户不能使用收费模型或 SQL 项目。
4. 恢复 AgentMesh 新版网页上传 → 私有图片 → 真实模型识图 → 历史追问 → 账单链路。沿用原 20 元累计预算，禁止重置账本；本次设计不产生模型调用。

当前所需信息仅为：发送验证码的 QQ 邮箱地址、SMTP 授权码的本机私有文件绝对路径、用户明确指定的测试收件邮箱。无需 QQ 登录密码、身份证或手机号；开启服务时的账号安全验证由邮箱持有人自行完成。正式云部署再提供域名与服务器配置。
